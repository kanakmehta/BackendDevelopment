# Part A — Conceptual Questions

## 1. What is `jsonb` in PostgreSQL, and how does it differ from the plain `json` type?

PostgreSQL provides both `json` and `jsonb` data types for storing JSON documents. The main difference is how the data is stored internally. The `json` type stores the JSON as **plain text**, preserving the original formatting, whitespace, and key order. PostgreSQL validates the JSON when it is inserted, but the text representation is retained. This can be useful when the original JSON representation needs to be preserved.

The `jsonb` type stores JSON in a **binary decomposed format**. PostgreSQL parses the JSON during insertion and stores it in a form that is optimized for processing and querying. Because the data is already decomposed, `jsonb` generally provides faster querying and supports powerful indexing mechanisms such as GIN indexes.

The trade-off is that `jsonb` requires more processing during insertion and does not preserve the original formatting or key order.

For example:

```sql
CREATE TABLE products (
    id SERIAL PRIMARY KEY,
    data JSONB
);

INSERT INTO products (data)
VALUES (
    '{"brand": "Dell", "ram": 16, "storage": "512GB"}'
);

SELECT data->>'brand'
FROM products;
```

The query returns:

```text
Dell
```

Therefore, `jsonb` is generally preferred when JSON data needs to be queried, filtered, or indexed frequently, while `json` is useful when preserving the original JSON text is important.

# 2. How can PostgreSQL work as both a SQL and a NoSQL database in the same table?

PostgreSQL can combine traditional relational SQL features with document-oriented NoSQL features by using a `jsonb` column inside a normal relational table. The fixed columns can store structured data with strict data types, while the `jsonb` column can store flexible attributes that may differ between rows.

For example, a product table can contain `id`, `name`, and `price` as strongly typed columns. An additional `attributes` column can contain JSONB data. A laptop can store RAM and CPU information, while a book can store author and page count, without requiring separate columns for every possible attribute.

Example schema:

```sql
CREATE TABLE products (
    id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    category VARCHAR(50) NOT NULL,
    price NUMERIC(10,2) NOT NULL,
    attributes JSONB
);
```

A laptop could contain:

```json
{
    "ram_gb": 16,
    "cpu": "Intel i7"
}
```

while a book could contain:

```json
{
    "author": "Robert C. Martin",
    "pages": 464
}
```

The normal columns provide relational features such as constraints, sorting, joins, and transactions. The JSONB column provides flexible document-style storage. Therefore, PostgreSQL can support both SQL and NoSQL-style data management within the same table without requiring a separate database system.

# 3. Give an example of a `jsonb` query using each of these operators: `->`, `->>`, `@>`, `?`

Consider the following JSONB value:

```json
{
    "brand": "Dell",
    "ram_gb": 16,
    "wireless": true,
    "specifications": {
        "cpu": "Intel i7"
    }
}
```

### `->` — returns JSON

```sql
SELECT attributes -> 'specifications'
FROM products
WHERE name = 'Dell Inspiron';
```

Output:

```json
{"cpu": "Intel i7"}
```

The `->` operator returns the selected value as a **JSON/JSONB value**.

### `->>` — returns text

```sql
SELECT attributes ->> 'brand'
FROM products
WHERE name = 'Dell Inspiron';
```

Output:

```text
Dell
```

The `->>` operator extracts the value as **text**.

### `@>` — containment

```sql
SELECT name
FROM products
WHERE attributes @> '{"wireless": true}';
```

Output:

```text
Logitech Wireless Mouse
```

This checks whether the JSONB document contains the specified key-value pair.

### `?` — key exists

```sql
SELECT name
FROM products
WHERE attributes ? 'ram_gb';
```

Output:

```text
Dell Inspiron
Lenovo ThinkPad
```

The `?` operator checks whether a specified key exists at the top level.

The major difference between `->` and `->>` is that `->` returns JSON/JSONB, while `->>` returns text. This difference matters when extracting values for further processing or comparison.

# 4. How can a GIN index on a `jsonb` column change query performance?

A GIN, or **Generalized Inverted Index**, is an index type that PostgreSQL can use with JSONB data. It is especially useful when queries need to search inside JSON documents for keys or key-value combinations.

Without an appropriate index, PostgreSQL may need to examine many rows in a table to determine which JSON documents satisfy a condition. This becomes expensive when the table contains thousands or millions of records.

For example:

```sql
CREATE INDEX idx_products_attributes
ON products
USING GIN (attributes);
```

A query such as:

```sql
SELECT name
FROM products
WHERE attributes @> '{"wireless": true}';
```

can use the GIN index to locate matching JSONB values more efficiently.

The GIN index is particularly useful for operators such as `@>` and key-existence operations such as `?`, `?|`, and `?&`, depending on the index operator class.

The performance can be examined using:

```sql
EXPLAIN ANALYZE
SELECT name
FROM products
WHERE attributes @> '{"wireless": true}';
```

On a small table containing only a few rows, PostgreSQL may still choose a sequential scan because scanning the entire table can actually be cheaper than using an index. Therefore, creating an index does not guarantee an index scan for every query.

For large JSONB datasets, however, a suitable GIN index can significantly reduce the amount of data PostgreSQL needs to inspect.

# 5. Where could PostgreSQL + `jsonb` replace a MongoDB deployment, and where would MongoDB still be the better fit?

PostgreSQL with JSONB can replace MongoDB in applications that need both relational and document-style data in the same database. PostgreSQL is especially useful when the application requires strong transactions, relationships between tables, SQL joins, constraints, and structured data alongside flexible JSON attributes.

For example, an e-commerce system could store fixed product information such as `id`, `name`, `category`, and `price` in normal columns while storing category-specific attributes in a JSONB column.

```sql
SELECT p.name, c.name
FROM products p
JOIN categories c
ON p.category = c.name
WHERE p.attributes @> '{"wireless": true}';
```

PostgreSQL provides mature transaction support and relational constraints, making it useful when data consistency and relationships are important.

MongoDB can be a better fit when the application is primarily document-oriented and has highly variable document structures. MongoDB is designed around collections and documents and can be convenient when application data naturally maps to independent JSON-like documents. MongoDB also provides horizontal scaling features suitable for workloads requiring distribution across multiple servers.

Therefore, the choice depends on the application. PostgreSQL + JSONB is useful when relational operations, transactions, joins, and flexible JSON data are needed together. MongoDB can be more appropriate when the application is predominantly document-based and requires a document-oriented architecture and horizontal scaling.

# Task 1 — Schema

Create a `products` table with fixed columns and one JSONB column:

```sql
CREATE TABLE products (
    id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    category VARCHAR(50) NOT NULL,
    price NUMERIC(10,2) NOT NULL,
    attributes JSONB
);
```

### Explanation

The table contains three normal relational attributes:

- `id` — unique identifier
- `name` — product name
- `category` — product category
- `price` — product price

The `attributes` column uses `JSONB` so that different categories can store different properties.

For example:

```text
Book
→ author, pages

Laptop
→ ram_gb, cpu

Accessory
→ color, wireless
```

This avoids creating separate columns for every possible product attribute.

# Task 3 — Query by Category-Specific Attribute

The objective is to write **one query per category** using an attribute unique to that category.

## Query 1 — Books

Find books written by James Clear:

```sql
SELECT
    name,
    attributes ->> 'author' AS author
FROM products
WHERE category = 'book'
AND attributes ->> 'author' = 'James Clear';
```

Expected result:

```text
name           | author
---------------|------------
Atomic Habits  | James Clear
```

---

## Query 2 — Laptops

Find laptops with at least 16 GB RAM:

```sql
SELECT
    name,
    attributes ->> 'ram_gb' AS ram_gb
FROM products
WHERE category = 'laptop'
AND (attributes ->> 'ram_gb')::int >= 16;
```

Expected result:

```text
Dell Inspiron    | 16
Lenovo ThinkPad  | 32
```

---

## Query 3 — Accessories

Find wireless accessories:

```sql
SELECT
    name,
    attributes ->> 'color' AS color
FROM products
WHERE category = 'accessory'
AND (attributes ->> 'wireless')::boolean = true;
```

Expected result:

```text
Logitech Wireless Mouse | black
```

These queries demonstrate that each category can have different JSONB attributes without changing the table schema.

# Task 4 — Containment Query

Use the JSONB containment operator `@>` to find products where a particular key-value pair exists.

```sql
SELECT name
FROM products
WHERE attributes @> '{"wireless": true}';
```

Expected result:

```text
Logitech Wireless Mouse
```

### Explanation

The `@>` operator checks whether the JSONB value on the left contains the JSONB value on the right.

Here:

```sql
attributes @> '{"wireless": true}'
```

means:

> Find rows whose `attributes` JSON contains `"wireless": true`.

This is especially useful for searching JSONB documents based on key-value combinations.

# Task 5 — Update JSONB Without Altering the Table

Add a new attribute called `discount_pct` to the wireless mouse.

```sql
UPDATE products
SET attributes = attributes || '{"discount_pct": 10}'
WHERE name = 'Logitech Wireless Mouse';
```

Verify the change:

```sql
SELECT
    name,
    attributes
FROM products
WHERE name = 'Logitech Wireless Mouse';
```

Expected JSON:

```json
{
    "color": "black",
    "wireless": true,
    "dpi": 1600,
    "discount_pct": 10
}
```

### Explanation

No `ALTER TABLE` command was required.

The `||` operator merges two JSONB objects:

```sql
attributes || '{"discount_pct": 10}'
```

This demonstrates one of the major benefits of JSONB: new attributes can be added to individual documents without changing the relational table schema.

# PostgreSQL vs MongoDB Comparison

| Feature | PostgreSQL + JSONB | MongoDB |
|---|---|---|
| Basic structure | Tables + rows | Collections + documents |
| Flexible data | JSONB columns | Native document model |
| SQL queries | Yes | No, uses MongoDB query language |
| Joins | Strong support | `$lookup` available |
| Transactions | Strong relational transactions | Supports transactions |
| Schema | Can combine strict + flexible fields | Flexible document schema |
| JSON querying | JSONB operators | Native document queries |
| JSON indexing | GIN and other indexes | MongoDB indexes |
| Horizontal scaling | Available through various architectures/tools | Core strength of MongoDB |
| Best suited for | Relational + flexible data | Document-oriented applications |

### Syntax comparison

PostgreSQL:

```sql
SELECT name
FROM products
WHERE attributes @> '{"wireless": true}';
```

MongoDB:

```javascript
db.products.find({
    "attributes.wireless": true
});
```

PostgreSQL uses SQL together with JSONB operators, while MongoDB uses a document-oriented query syntax.
